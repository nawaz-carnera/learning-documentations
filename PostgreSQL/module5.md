## 1. PRIMARY KEY

A **primary key** uniquely identifies every row in a table. It enforces two rules at once:
- `UNIQUE` — no two rows can have the same PK value
- `NOT NULL` — the PK column can never be NULL

Every table should have one primary key. PostgreSQL automatically creates a **unique B-tree index** on the primary key column(s).

---

### Single Column Primary Key

**Inline (column-level) — most common:**
```sql
CREATE TABLE users (
  id    SERIAL PRIMARY KEY,
  email TEXT NOT NULL
);
```

**Table-level (explicit, named):**
```sql
CREATE TABLE users (
  id    SERIAL,
  email TEXT NOT NULL,
  CONSTRAINT users_pkey PRIMARY KEY (id)
);
```

**Modern syntax using IDENTITY (PostgreSQL 10+):**
```sql
CREATE TABLE users (
  id    INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email TEXT NOT NULL
);

-- GENERATED ALWAYS: PostgreSQL controls the value, manual insert blocked
-- GENERATED BY DEFAULT: you can override the value on insert if needed
CREATE TABLE users (
  id    INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  email TEXT NOT NULL
);
```

> **Edge Case — SERIAL vs IDENTITY:**
> `SERIAL` is a shorthand that creates a sequence behind the scenes and grants usage to the table owner. `GENERATED AS IDENTITY` is the SQL-standard way (Postgres 10+) and is tightly coupled to the column — the sequence is owned by the column and drops with it. Prefer `IDENTITY` for new tables.

> **Edge Case — Inserting into GENERATED ALWAYS AS IDENTITY:**
> ```sql
> INSERT INTO users (id, email) VALUES (99, 'a@b.com');
> -- ERROR: cannot insert into column "id"
> -- DETAIL: Column "id" is an identity column defined as GENERATED ALWAYS.
>
> -- Override with OVERRIDING SYSTEM VALUE (use sparingly, e.g. data migrations):
> INSERT INTO users (id, email) OVERRIDING SYSTEM VALUE VALUES (99, 'a@b.com');
> ```

---

### Composite Primary Key

A **composite (compound) primary key** uses two or more columns together to uniquely identify a row. Neither column alone needs to be unique — the combination must be.

```sql
-- Order items: one order can have many products, but each product appears once per order
CREATE TABLE order_items (
  order_id    INTEGER   NOT NULL,
  product_id  INTEGER   NOT NULL,
  quantity    INTEGER   NOT NULL DEFAULT 1,
  unit_price  NUMERIC(10,2) NOT NULL,
  PRIMARY KEY (order_id, product_id)   -- composite PK
);
```

```sql
-- Student enrollments: one student can enroll in many courses
CREATE TABLE enrollments (
  student_id  INTEGER NOT NULL,
  course_id   INTEGER NOT NULL,
  enrolled_at DATE    NOT NULL DEFAULT CURRENT_DATE,
  PRIMARY KEY (student_id, course_id)
);
```

```sql
-- Insert: both columns together must be unique
INSERT INTO order_items VALUES (1, 101, 2, 29.99);  -- OK
INSERT INTO order_items VALUES (1, 102, 1, 49.99);  -- OK (different product_id)
INSERT INTO order_items VALUES (1, 101, 5, 29.99);  -- ERROR: duplicate key (1, 101)
```

> **Edge Case:** With a composite PK, you can still have duplicate values in individual columns — only the combination must be unique:
> ```sql
> -- Both rows have order_id = 1, both have product_id = 101 — but together they differ
> -- Actually this would fail since (1,101) is duplicate. Let's clarify:
> INSERT INTO order_items VALUES (1, 101, 2, 29.99);  -- OK
> INSERT INTO order_items VALUES (2, 101, 3, 29.99);  -- OK: order_id differs
> INSERT INTO order_items VALUES (1, 101, 1, 19.99);  -- ERROR: (1,101) already exists
> ```

> **Edge Case:** Composite PKs make foreign key references more verbose — the referencing table must include all PK columns:
> ```sql
> CREATE TABLE item_discounts (
>   order_id   INTEGER,
>   product_id INTEGER,
>   discount   NUMERIC(5,2),
>   FOREIGN KEY (order_id, product_id) REFERENCES order_items (order_id, product_id)
> );
> ```

---

### Natural vs Surrogate Keys

| | Natural Key | Surrogate Key |
|---|---|---|
| Definition | A real-world attribute (email, SSN, ISBN) | An artificial ID (SERIAL, UUID) |
| Example | `email TEXT PRIMARY KEY` | `id SERIAL PRIMARY KEY` |
| Pros | Meaningful, no extra column needed | Stable, never changes, compact |
| Cons | Can change (email changes), may be long | Meaningless by itself |
| Recommendation | Use as UNIQUE constraint, not PK | Prefer as PK |

```sql
-- Recommended pattern: surrogate PK + natural key as UNIQUE
CREATE TABLE users (
  id       SERIAL PRIMARY KEY,           -- surrogate
  email    TEXT   UNIQUE NOT NULL,       -- natural, enforced unique
  username TEXT   UNIQUE NOT NULL
);
```

## 2. UNIQUE Constraints

A `UNIQUE` constraint ensures no two rows have the same value in the specified column(s). Unlike `PRIMARY KEY`, a unique column **can contain NULL** — and multiple NULLs are allowed (because `NULL ≠ NULL` in SQL).

---

### Single Column UNIQUE

**Inline:**
```sql
CREATE TABLE users (
  id       SERIAL PRIMARY KEY,
  email    TEXT UNIQUE NOT NULL,
  username TEXT UNIQUE
);
```

**Table-level (named):**
```sql
CREATE TABLE users (
  id       SERIAL,
  email    TEXT NOT NULL,
  username TEXT,
  CONSTRAINT users_email_unique    UNIQUE (email),
  CONSTRAINT users_username_unique UNIQUE (username)
);
```

---

### Composite UNIQUE

A composite unique constraint means the **combination** of columns must be unique.

```sql
-- A user can have multiple phone numbers, but each (user_id, phone_type) pair must be unique
CREATE TABLE user_phones (
  id         SERIAL PRIMARY KEY,
  user_id    INTEGER NOT NULL,
  phone_type TEXT    NOT NULL,   -- 'mobile', 'home', 'work'
  number     TEXT    NOT NULL,
  CONSTRAINT user_phones_type_unique UNIQUE (user_id, phone_type)
);

INSERT INTO user_phones (user_id, phone_type, number) VALUES (1, 'mobile', '555-1234'); -- OK
INSERT INTO user_phones (user_id, phone_type, number) VALUES (1, 'home',   '555-5678'); -- OK
INSERT INTO user_phones (user_id, phone_type, number) VALUES (1, 'mobile', '555-9999'); -- ERROR
```

> **Edge Case — NULL in UNIQUE columns:**
> ```sql
> CREATE TABLE products (sku TEXT UNIQUE);
>
> INSERT INTO products VALUES (NULL);  -- OK
> INSERT INTO products VALUES (NULL);  -- Also OK! Multiple NULLs allowed in UNIQUE
> INSERT INTO products VALUES ('ABC'); -- OK
> INSERT INTO products VALUES ('ABC'); -- ERROR: duplicate key
> ```
> This follows the SQL standard: `NULL` means "unknown", and two unknowns are not considered equal.
> If you want to prevent multiple NULLs, add `NOT NULL` alongside `UNIQUE`.

> **Edge Case — UNIQUE creates an index:** Every `UNIQUE` constraint automatically creates a unique B-tree index. Adding a duplicate `CREATE UNIQUE INDEX` on the same column is redundant.

---

### UNIQUE vs PRIMARY KEY

| | PRIMARY KEY | UNIQUE |
|---|---|---|
| Allows NULL | No | Yes (multiple NULLs ok) |
| Number per table | Only one | Multiple allowed |
| Creates index | Yes (unique B-tree) | Yes (unique B-tree) |
| Can be referenced by FK | Yes | Yes |
| Meaning | The row identifier | Just an alternate unique attribute |

## 3. NOT NULL

`NOT NULL` ensures a column always has a value — it can never be `NULL`.

### Inline (most common)
```sql
CREATE TABLE employees (
  id         SERIAL       PRIMARY KEY,
  first_name VARCHAR(100) NOT NULL,
  last_name  VARCHAR(100) NOT NULL,
  email      TEXT         NOT NULL,
  phone      TEXT                    -- nullable: phone is optional
);
```

### What NULL means
`NULL` means **unknown** or **absent** — it is not zero, not empty string, not false.

```sql
SELECT NULL = NULL;    -- NULL  (not TRUE — unknowns can't be equal)
SELECT NULL IS NULL;   -- TRUE  (use IS NULL / IS NOT NULL to check)
SELECT 5 + NULL;       -- NULL  (any arithmetic with NULL returns NULL)
SELECT '' = NULL;      -- NULL  (empty string is not NULL)
```

> **Edge Case — NULL in WHERE clauses:**
> ```sql
> -- This will NOT return rows where phone IS NULL:
> SELECT * FROM employees WHERE phone = NULL;   -- returns nothing
>
> -- Correct way:
> SELECT * FROM employees WHERE phone IS NULL;
> SELECT * FROM employees WHERE phone IS NOT NULL;
> ```

> **Edge Case — NOT NULL and DEFAULT together:**
> ```sql
> -- A NOT NULL column without a DEFAULT will require every INSERT to supply a value
> ALTER TABLE employees ADD COLUMN department TEXT NOT NULL;
> -- ERROR on existing rows — must pair with DEFAULT:
> ALTER TABLE employees ADD COLUMN department TEXT NOT NULL DEFAULT 'General';
> ```

> **Edge Case — COUNT behavior with NULL:**
> ```sql
> SELECT COUNT(*)     FROM employees;  -- counts all rows including NULLs
> SELECT COUNT(phone) FROM employees;  -- counts only rows where phone IS NOT NULL
> ```

## 4. CHECK Constraints

A `CHECK` constraint ensures a column value satisfies a boolean expression. The row is rejected if the expression evaluates to `FALSE` (but `NULL` passes — because `NULL` is not `FALSE`).

---

### Column-Level CHECK

```sql
CREATE TABLE products (
  id       SERIAL PRIMARY KEY,
  name     TEXT           NOT NULL,
  price    NUMERIC(10,2)  NOT NULL CHECK (price >= 0),
  quantity INTEGER        NOT NULL CHECK (quantity >= 0),
  rating   NUMERIC(2,1)           CHECK (rating BETWEEN 1.0 AND 5.0)
);

INSERT INTO products (name, price, quantity) VALUES ('Widget', -5.00, 10);
-- ERROR: new row violates check constraint "products_price_check"
```

---

### Table-Level CHECK

Use table-level when the check involves **more than one column**:

```sql
CREATE TABLE discounts (
  id             SERIAL PRIMARY KEY,
  discount_start DATE NOT NULL,
  discount_end   DATE NOT NULL,
  CHECK (discount_end > discount_start)   -- cross-column check
);

CREATE TABLE employees (
  id         SERIAL PRIMARY KEY,
  first_name TEXT NOT NULL,
  last_name  TEXT NOT NULL,
  salary     NUMERIC(10,2),
  bonus      NUMERIC(10,2),
  CHECK (bonus <= salary * 0.5)   -- bonus can't exceed 50% of salary
);
```

---

### Named CHECK Constraints

Always name your constraints — unnamed ones get auto-generated names that are hard to identify in error messages.

```sql
CREATE TABLE orders (
  id       SERIAL PRIMARY KEY,
  status   TEXT         NOT NULL,
  quantity INTEGER      NOT NULL,
  amount   NUMERIC(10,2) NOT NULL,

  CONSTRAINT orders_status_valid
    CHECK (status IN ('pending', 'confirmed', 'shipped', 'delivered', 'cancelled')),

  CONSTRAINT orders_quantity_positive
    CHECK (quantity > 0),

  CONSTRAINT orders_amount_positive
    CHECK (amount > 0)
);

-- Named constraint gives a clear error:
INSERT INTO orders (status, quantity, amount) VALUES ('unknown', 1, 10.00);
-- ERROR: new row violates check constraint "orders_status_valid"
-- vs unnamed: "orders_status_check" (vague, auto-generated)
```

> **Edge Case — NULL bypasses CHECK:**
> ```sql
> CREATE TABLE products (rating NUMERIC CHECK (rating BETWEEN 1 AND 5));
>
> INSERT INTO products (rating) VALUES (NULL);  -- OK! NULL is not FALSE
> INSERT INTO products (rating) VALUES (10);    -- ERROR: check constraint violated
>
> -- To block NULLs too, combine with NOT NULL:
> rating NUMERIC NOT NULL CHECK (rating BETWEEN 1 AND 5)
> ```

> **Edge Case — CHECK is not enforced across rows:** CHECK only validates the current row being inserted or updated. It cannot reference other rows or other tables — that requires a trigger or a more complex constraint.
> ```sql
> -- This is NOT valid — CHECK cannot query other tables:
> CHECK (user_id IN (SELECT id FROM users))  -- ERROR at definition time
> -- Use a FOREIGN KEY instead for referential integrity.
> ```

> **Edge Case — Immutable functions in CHECK:** CHECK expressions must be immutable. Avoid `NOW()`, `CURRENT_DATE`, or any volatile function — they produce unpredictable results:
> ```sql
> -- BAD: volatile function in CHECK
> CHECK (created_at <= NOW())  -- may behave unexpectedly

> -- Use a trigger instead for time-based validation
> ```

## 5. DEFAULT Values

A `DEFAULT` provides an automatic value when no value is supplied during `INSERT`.

### Static Defaults

```sql
CREATE TABLE orders (
  id          SERIAL         PRIMARY KEY,
  status      TEXT           NOT NULL DEFAULT 'pending',
  quantity    INTEGER        NOT NULL DEFAULT 1,
  is_gift     BOOLEAN        NOT NULL DEFAULT false,
  notes       TEXT                    DEFAULT NULL,
  created_at  TIMESTAMPTZ    NOT NULL DEFAULT NOW()
);

-- Only supply what differs from defaults
INSERT INTO orders (status) VALUES ('confirmed');
-- id → auto from SERIAL
-- quantity → 1
-- is_gift → false
-- notes → NULL
-- created_at → current timestamp
```

### Dynamic Defaults (functions)

```sql
CREATE TABLE sessions (
  id          UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
  token       TEXT         NOT NULL    DEFAULT md5(random()::TEXT),
  expires_at  TIMESTAMPTZ  NOT NULL    DEFAULT NOW() + INTERVAL '7 days',
  created_at  TIMESTAMPTZ  NOT NULL    DEFAULT NOW()
);
```

### Sequence as Default (manual, without SERIAL)

```sql
CREATE SEQUENCE order_number_seq START 1000 INCREMENT 1;

CREATE TABLE orders (
  order_number INTEGER PRIMARY KEY DEFAULT nextval('order_number_seq'),
  total        NUMERIC(10,2)
);
```

> **Edge Case — DEFAULT is not the same as NOT NULL:**
> ```sql
> ALTER TABLE orders ALTER COLUMN notes SET DEFAULT 'N/A';
>
> -- Existing rows are NOT updated — DEFAULT only applies to future inserts
> UPDATE orders SET notes = 'N/A' WHERE notes IS NULL;  -- do this manually
> ```

> **Edge Case — Explicit NULL overrides DEFAULT:**
> ```sql
> INSERT INTO orders (status, notes) VALUES ('pending', NULL);
> -- notes = NULL, not the default — explicit NULL wins over DEFAULT
> -- To prevent this, add NOT NULL alongside DEFAULT
> ```

> **Edge Case — DEFAULT with GENERATED ALWAYS AS (computed columns):**
> ```sql
> CREATE TABLE rectangles (
>   width  NUMERIC,
>   height NUMERIC,
>   area   NUMERIC GENERATED ALWAYS AS (width * height) STORED
>   -- "area" is auto-computed, cannot be manually inserted/updated
> );
> ```

## 6. FOREIGN KEY

A **foreign key** enforces **referential integrity** — it ensures a value in one table's column exists in another table's primary (or unique) key column.

```
orders.user_id  →  users.id
   child table      parent table
```

The table with the FK is the **child** (referencing table).
The table being pointed to is the **parent** (referenced table).

---

### Basic Foreign Key

```sql
-- Parent table
CREATE TABLE users (
  id    SERIAL PRIMARY KEY,
  name  TEXT NOT NULL
);

-- Child table
CREATE TABLE orders (
  id         SERIAL  PRIMARY KEY,
  user_id    INTEGER NOT NULL REFERENCES users(id),
  total      NUMERIC(10,2),
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Insert: parent row must exist first
INSERT INTO users (name) VALUES ('Alice');          -- id = 1
INSERT INTO orders (user_id, total) VALUES (1, 99.99);  -- OK
INSERT INTO orders (user_id, total) VALUES (999, 50.00); -- ERROR: key (999) not in users
```

**Named FK (table-level — recommended):**
```sql
CREATE TABLE orders (
  id      SERIAL PRIMARY KEY,
  user_id INTEGER NOT NULL,
  total   NUMERIC(10,2),
  CONSTRAINT orders_user_id_fkey
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

---

### ON DELETE Behaviors

Defines what happens to child rows when the **parent row is deleted**.

```sql
FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE <action>
```

| Action | Behavior | Use When |
|---|---|---|
| `NO ACTION` | Error if child rows exist (default, checked at end of transaction) | You want to block delete if children exist |
| `RESTRICT` | Error immediately if child rows exist | Same as NO ACTION but checked immediately |
| `CASCADE` | Delete child rows automatically | Orders deleted when user is deleted |
| `SET NULL` | Set FK column to NULL in child rows | Orders kept, but user_id cleared |
| `SET DEFAULT` | Set FK column to its DEFAULT value | Orders assigned to a default user |

```sql
-- CASCADE: delete user → all their orders are also deleted
CREATE TABLE orders (
  id      SERIAL  PRIMARY KEY,
  user_id INTEGER REFERENCES users(id) ON DELETE CASCADE
);

-- SET NULL: delete user → orders remain, user_id becomes NULL
CREATE TABLE orders (
  id      SERIAL  PRIMARY KEY,
  user_id INTEGER REFERENCES users(id) ON DELETE SET NULL
);

-- SET DEFAULT: delete user → orders assigned to user_id = 0 (a "guest" user)
CREATE TABLE orders (
  id      SERIAL  PRIMARY KEY,
  user_id INTEGER DEFAULT 0 REFERENCES users(id) ON DELETE SET DEFAULT
);

-- RESTRICT: delete user → error if any orders exist (strict, immediate)
CREATE TABLE orders (
  id      SERIAL  PRIMARY KEY,
  user_id INTEGER REFERENCES users(id) ON DELETE RESTRICT
);
```

**Visual summary:**
```
Parent row deleted →

NO ACTION / RESTRICT  →  ERROR (cannot delete parent while children exist)
CASCADE               →  child rows deleted automatically
SET NULL              →  child FK column = NULL
SET DEFAULT           →  child FK column = default value
```

> **Edge Case — NO ACTION vs RESTRICT:**
> Both block deletes when children exist, but `RESTRICT` is checked immediately (within the statement), while `NO ACTION` is deferred to end-of-transaction. This matters with deferrable constraints and triggers that delete children before the parent in the same transaction.

> **Edge Case — CASCADE can silently delete a lot of data:**
> ```sql
> DELETE FROM users WHERE id = 1;
> -- With ON DELETE CASCADE on orders, and cascade on order_items pointing to orders:
> -- users row deleted → orders deleted → order_items deleted (chain reaction)
> -- No warning, no confirmation. Be intentional with CASCADE depth.
> ```

---

### ON UPDATE Behaviors

Defines what happens to child rows when the **parent's PK value is updated**.

```sql
FOREIGN KEY (user_id) REFERENCES users(id) ON UPDATE <action>
```

| Action | Behavior |
|---|---|
| `NO ACTION` | Error if child rows exist (default) |
| `RESTRICT` | Immediate error if child rows exist |
| `CASCADE` | Update child FK column to match new parent PK |
| `SET NULL` | Set child FK column to NULL |
| `SET DEFAULT` | Set child FK column to its default |

```sql
-- CASCADE update: if user.id changes from 1 to 99, orders.user_id also becomes 99
CREATE TABLE orders (
  id      SERIAL  PRIMARY KEY,
  user_id INTEGER REFERENCES users(id) ON DELETE CASCADE ON UPDATE CASCADE
);
```

> **Edge Case:** In well-designed schemas using `SERIAL` or `UUID` PKs, the PK value almost never changes. `ON UPDATE CASCADE` is rarely needed — but it's critical in legacy systems where natural keys (like email or username) are used as PKs and can change.

---

### Composite Foreign Keys

When the parent table has a composite primary key, the FK must reference all columns:

```sql
CREATE TABLE order_items (
  order_id   INTEGER,
  product_id INTEGER,
  quantity   INTEGER NOT NULL,
  PRIMARY KEY (order_id, product_id)
);

CREATE TABLE item_reviews (
  id         SERIAL PRIMARY KEY,
  order_id   INTEGER NOT NULL,
  product_id INTEGER NOT NULL,
  rating     INTEGER CHECK (rating BETWEEN 1 AND 5),
  CONSTRAINT item_reviews_fkey
    FOREIGN KEY (order_id, product_id)
    REFERENCES order_items (order_id, product_id)
    ON DELETE CASCADE
);
```

---

### Self-Referencing Foreign Keys

A table can have a FK that points to itself — useful for hierarchies (org charts, categories, comment threads).

```sql
CREATE TABLE employees (
  id         SERIAL  PRIMARY KEY,
  name       TEXT    NOT NULL,
  manager_id INTEGER REFERENCES employees(id) ON DELETE SET NULL
  -- manager_id points to another row in the same table
);

INSERT INTO employees (name, manager_id) VALUES ('CEO', NULL);       -- id=1, no manager
INSERT INTO employees (name, manager_id) VALUES ('VP Eng', 1);       -- id=2, reports to CEO
INSERT INTO employees (name, manager_id) VALUES ('Engineer', 2);     -- id=3, reports to VP

-- Query the hierarchy
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```

```sql
-- Recursive category tree
CREATE TABLE categories (
  id        SERIAL PRIMARY KEY,
  name      TEXT NOT NULL,
  parent_id INTEGER REFERENCES categories(id) ON DELETE CASCADE
);
```

> **Edge Case — Circular self-references:** PostgreSQL allows you to create them, but they can cause infinite loops in recursive queries. Always add a depth limit:
> ```sql
> WITH RECURSIVE org_chart AS (
>   SELECT id, name, manager_id, 0 AS depth
>   FROM employees WHERE manager_id IS NULL
>   UNION ALL
>   SELECT e.id, e.name, e.manager_id, oc.depth + 1
>   FROM employees e
>   JOIN org_chart oc ON e.manager_id = oc.id
>   WHERE oc.depth < 10   -- safety limit to prevent infinite recursion
> )
> SELECT * FROM org_chart;
> ```

## 7. Adding and Removing Constraints on Existing Tables

---

### Adding Constraints

```sql
-- Add PRIMARY KEY
ALTER TABLE employees ADD CONSTRAINT employees_pkey PRIMARY KEY (id);

-- Add UNIQUE
ALTER TABLE users ADD CONSTRAINT users_email_unique UNIQUE (email);

-- Add UNIQUE on multiple columns
ALTER TABLE user_phones
  ADD CONSTRAINT user_phones_type_unique UNIQUE (user_id, phone_type);

-- Add CHECK
ALTER TABLE products
  ADD CONSTRAINT products_price_positive CHECK (price >= 0);

-- Add NOT NULL (different syntax — uses ALTER COLUMN)
ALTER TABLE employees ALTER COLUMN email SET NOT NULL;

-- Add FOREIGN KEY
ALTER TABLE orders
  ADD CONSTRAINT orders_user_id_fkey
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE;

-- Add DEFAULT (not technically a constraint but related)
ALTER TABLE orders ALTER COLUMN status SET DEFAULT 'pending';
```

> **Edge Case — Adding a constraint to a table with existing data:**
> The constraint is validated immediately against all existing rows. If any row violates it, the `ALTER TABLE` fails:
> ```sql
> -- If any price < 0 exists, this will fail:
> ALTER TABLE products ADD CONSTRAINT products_price_positive CHECK (price >= 0);
> -- ERROR: check constraint "products_price_positive" is violated by some row
>
> -- Fix: clean the data first
> UPDATE products SET price = 0 WHERE price < 0;
> ALTER TABLE products ADD CONSTRAINT products_price_positive CHECK (price >= 0);
> ```

> **Edge Case — Adding FK to large tables (locks):**
> `ALTER TABLE ... ADD FOREIGN KEY` acquires a lock and validates all rows. On large production tables, this can block reads/writes for a long time. Use `NOT VALID` to skip initial validation, then validate in the background:
> ```sql
> -- Step 1: Add FK without validating existing rows (fast, non-blocking)
> ALTER TABLE orders
>   ADD CONSTRAINT orders_user_id_fkey
>   FOREIGN KEY (user_id) REFERENCES users(id)
>   NOT VALID;
>
> -- Step 2: Validate existing rows separately (uses weaker lock, can run concurrently)
> ALTER TABLE orders VALIDATE CONSTRAINT orders_user_id_fkey;
> ```

---

### Removing Constraints

```sql
-- Drop any named constraint (PK, UNIQUE, CHECK, FK)
ALTER TABLE orders DROP CONSTRAINT orders_user_id_fkey;

-- Safe drop (no error if constraint doesn't exist)
ALTER TABLE orders DROP CONSTRAINT IF EXISTS orders_user_id_fkey;

-- Drop NOT NULL
ALTER TABLE employees ALTER COLUMN phone DROP NOT NULL;

-- Drop DEFAULT
ALTER TABLE orders ALTER COLUMN status DROP DEFAULT;

-- Drop PRIMARY KEY
ALTER TABLE employees DROP CONSTRAINT employees_pkey;
```

> **Edge Case — Dropping a PRIMARY KEY that is referenced by a FK:**
> ```sql
> ALTER TABLE users DROP CONSTRAINT users_pkey;
> -- ERROR: cannot drop constraint users_pkey on table users because
> --        other objects depend on it
> -- DETAIL: constraint orders_user_id_fkey on table orders depends on it
>
> -- Must drop the FK first, then the PK:
> ALTER TABLE orders DROP CONSTRAINT orders_user_id_fkey;
> ALTER TABLE users  DROP CONSTRAINT users_pkey;
> ```

> **Edge Case — Dropping a UNIQUE constraint vs a UNIQUE index:**
> A `UNIQUE` constraint is backed by an index. You drop the constraint (not the index directly):
> ```sql
> -- Correct: drop the constraint
> ALTER TABLE users DROP CONSTRAINT users_email_unique;
>
> -- This also works if it was created as a standalone index (not a constraint):
> DROP INDEX users_email_unique;
>
> -- But you cannot DROP INDEX for a constraint-backed index — drop the constraint instead
> ```

---

### Listing Constraints

```sql
-- In psql: describe table with constraints
\d tablename

-- List all constraints in current database
SELECT
  tc.table_name,
  tc.constraint_name,
  tc.constraint_type,
  kcu.column_name
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu
  ON tc.constraint_name = kcu.constraint_name
  AND tc.table_schema = kcu.table_schema
WHERE tc.table_schema = 'public'
ORDER BY tc.table_name, tc.constraint_type;

-- List foreign keys with their referenced tables
SELECT
  tc.table_name        AS child_table,
  kcu.column_name      AS child_column,
  ccu.table_name       AS parent_table,
  ccu.column_name      AS parent_column,
  rc.delete_rule       AS on_delete,
  rc.update_rule       AS on_update
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu
  ON tc.constraint_name = kcu.constraint_name
JOIN information_schema.referential_constraints rc
  ON tc.constraint_name = rc.constraint_name
JOIN information_schema.constraint_column_usage ccu
  ON rc.unique_constraint_name = ccu.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY'
ORDER BY tc.table_name;

-- Check constraint definitions
SELECT conname AS constraint_name, pg_get_constraintdef(oid) AS definition
FROM pg_constraint
WHERE conrelid = 'orders'::regclass;
```

### Disabling and Deferring Constraints

Sometimes (e.g., bulk data loads) you need to temporarily disable FK checks.

**Disable FK triggers for a session (superuser only):**
```sql
SET session_replication_role = 'replica';
-- Now FK constraints are not enforced
-- ... do your bulk inserts ...
SET session_replication_role = 'origin';  -- re-enable
```

**Deferrable constraints** — delay validation until end of transaction (useful for circular FKs or batch inserts):
```sql
CREATE TABLE a (
  id  INTEGER PRIMARY KEY,
  b_id INTEGER
);
CREATE TABLE b (
  id  INTEGER PRIMARY KEY,
  a_id INTEGER
);

ALTER TABLE a ADD CONSTRAINT a_b_fkey
  FOREIGN KEY (b_id) REFERENCES b(id)
  DEFERRABLE INITIALLY DEFERRED;

ALTER TABLE b ADD CONSTRAINT b_a_fkey
  FOREIGN KEY (a_id) REFERENCES a(id)
  DEFERRABLE INITIALLY DEFERRED;

-- Now you can insert both in one transaction without FK errors:
BEGIN;
  INSERT INTO a VALUES (1, 2);   -- b(2) doesn't exist yet — deferred, ok
  INSERT INTO b VALUES (2, 1);   -- a(1) now exists
COMMIT;  -- FK checked here — both exist, all good
```

| Deferral Option | Meaning |
|---|---|
| `NOT DEFERRABLE` | Always checked immediately (default) |
| `DEFERRABLE INITIALLY IMMEDIATE` | Deferrable, but checked immediately by default |
| `DEFERRABLE INITIALLY DEFERRED` | Checked at end of transaction by default |

## Quick Reference

```sql
-- PRIMARY KEY
id SERIAL PRIMARY KEY                                      -- inline, single
id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY        -- modern standard
PRIMARY KEY (col1, col2)                                   -- composite, table-level

-- UNIQUE
email TEXT UNIQUE
CONSTRAINT uq_name UNIQUE (col)
CONSTRAINT uq_name UNIQUE (col1, col2)                     -- composite unique

-- NOT NULL
col TEXT NOT NULL
ALTER TABLE t ALTER COLUMN col SET NOT NULL;
ALTER TABLE t ALTER COLUMN col DROP NOT NULL;

-- CHECK
price NUMERIC CHECK (price >= 0)
CONSTRAINT ck_name CHECK (col IN ('a','b','c'))
CONSTRAINT ck_name CHECK (end_date > start_date)           -- cross-column

-- DEFAULT
status TEXT DEFAULT 'pending'
created_at TIMESTAMPTZ DEFAULT NOW()
ALTER TABLE t ALTER COLUMN col SET DEFAULT 'value';
ALTER TABLE t ALTER COLUMN col DROP DEFAULT;

-- FOREIGN KEY
user_id INTEGER REFERENCES users(id)
user_id INTEGER REFERENCES users(id) ON DELETE CASCADE
user_id INTEGER REFERENCES users(id) ON DELETE SET NULL ON UPDATE CASCADE
CONSTRAINT fk_name FOREIGN KEY (col) REFERENCES parent(id) ON DELETE CASCADE

-- ON DELETE options: NO ACTION | RESTRICT | CASCADE | SET NULL | SET DEFAULT

-- Adding constraints
ALTER TABLE t ADD CONSTRAINT ck_name CHECK (price > 0);
ALTER TABLE t ADD CONSTRAINT fk_name FOREIGN KEY (col) REFERENCES other(id);
ALTER TABLE t ADD CONSTRAINT uq_name UNIQUE (col);
ALTER TABLE t ADD CONSTRAINT pk_name PRIMARY KEY (col);

-- Removing constraints
ALTER TABLE t DROP CONSTRAINT IF EXISTS constraint_name;
ALTER TABLE t ALTER COLUMN col DROP NOT NULL;
ALTER TABLE t ALTER COLUMN col DROP DEFAULT;

-- List constraints
\d tablename
SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid = 'tbl'::regclass;

-- NOT VALID + VALIDATE (production-safe FK addition)
ALTER TABLE t ADD CONSTRAINT fk_name FOREIGN KEY (col) REFERENCES other(id) NOT VALID;
ALTER TABLE t VALIDATE CONSTRAINT fk_name;
```
